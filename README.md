# 用途视图脱敏策略引擎（本地演示）

同一份客户/订单明细要同时服务 **运营（operations）、分析（analytics）、外包（outsourcing）**
三个用途。本项目实现的不是"前端隐藏几列"，而是一个在**数据执行层**强制生效的
用途视图引擎：关联、分组、导出、缓存全部经过同一套策略校验，规则升级期间不存在
部分接口仍按旧范围出数的窗口。

所有数据均为代码生成的**虚构数据**，不对应任何真实个人。

---

## 1. 架构选型：预生成独立物理视图 vs 查询时改写

两条路线都能实现"按用途出数"，本项目选择 **查询时改写为主 + 版本化缓存/导出为辅**。

| 维度 | 纯预生成独立物理视图 | 查询时改写（本项目） |
|---|---|---|
| **规则模型** | 每个用途/版本把数据物化成独立表或物理视图，查询直接打物化结果 | 逻辑查询经统一执行器编译到**版本化虚拟视图**（`v<版本>_<用途>_<表>`），原始表不对用途开放 |
| **新鲜度** | 源数据变更后要刷新全部物化副本，三用途 × N 版本的刷新窗口内会读到陈旧数据；刷新失败会产生版本间不一致 | 视图定义只存规则不存数据，每次查询实时读源表，**天然最新**；缓存只做结果加速且以策略版本为键 |
| **计算成本** | 刷新时一次性付全量重算成本，查询本身便宜；但用途/版本越多，存储与重复计算越重 | 每次查询承担改写与聚合成本；通过版本键 LRU 缓存摊薄热点查询，缓存命中率可在接口/审计中观测 |
| **规则撤回/升级** | 必须逐个物理视图替换或删除，替换窗口内可能新旧副本并存；已导出的物化文件散落各处难以追回 | 发布在**单事务**内完成（建视图→切活动版本→清缓存→撤旧导出），提交前任何一步失败整体回滚，对外原子切换；旧导出任务统一置 `revoked` |
| **可关联标识控制** | 物化时需为每个用途派生独立伪标识，跨用途密钥管理复杂 | 伪标识由 `HMAC(用途|版本|salt, 原始id)` 在视图表达式内派生，不同用途密钥域不同，**跨用途天然不可关联** |
| **小群体（k 匿名）** | 物化明细本身仍可能被小群体定向过滤，需要额外保护层 | 执行器对分组查询强制 `HAVING COUNT(*) >= k`，明细查询要求 `allow_detail`，在编译期拦截 |

**为什么不是二选一的极端：** 本项目的版本化视图是 SQLite 虚拟视图（只存定义不存数据），
兼顾了"视图"的强边界与"改写"的新鲜度；对重分析场景，缓存层就是按需物化——
但缓存键含策略版本，发布即失效，因此缓存永远不会成为绕过新规则的旁路。

### 新鲜度、计算成本、规则撤回的具体结论

- **新鲜度**：源表写入后下一次查询即可见，无副本刷新延迟；代价是每次查询实时计算。
- **计算成本**：受限 SELECT + 聚合在视图上完成，热点查询走 LRU 缓存（默认 256 条，
  响应中的 `cache_hit` 与审计日志可观测）；发布瞬间清缓存，之后冷启动重算。
- **规则撤回**：发布事务把所有 `done` 导出置为 `revoked` 并删除结果文件，
  下载接口拒绝撤回任务；队列中/重启恢复的任务**按当前活动版本重算**，
  不复用任务创建时的旧结果（见 `app/jobs.py`）。

## 2. 规则在执行层如何强制（不是前端隐藏列）

一次请求的完整链路：

```
结构化逻辑查询（JSON，非 SQL）
  → Executor 读取活动策略版本
  → 定位版本化用途视图（视图内已固化 列变换 + 行过滤）
  → 列级白名单校验（过滤/分组/排序/聚合/关联键）
  → 关联白名单校验（仅策略声明的外键路径，且关联键必须已暴露）
  → k 匿名编译（分组强制 HAVING；明细要求 allow_detail）
  → 版本键缓存查找 → 执行 → 写审计日志
```

规则手段是组合式的，单靠任何一项都不够：

| 手段 | 实现 | 防什么 |
|---|---|---|
| 直接标识遮蔽 | `mask_name/phone/email/id_card/detail` 字符串截断 | 屏幕上的直接标识泄露 |
| 伪标识化 | HMAC-SHA256 派生 `p_xxxxxxxx`，密钥按 `用途\|版本\|salt` 隔离 | 跨用途/跨版本关联同一人 |
| 泛化 | 年龄 10 岁桶、日期降为月、地址截断 | 准标识符过度精确导致的重识别 |
| 行范围过滤 | 视图定义内 `WHERE city IN (...)` / `channel IN (...)` | 外包越权看到未授权城市/渠道 |
| k 匿名 | 分组 `HAVING COUNT(*) >= k`，并返回被抑制小组数 | 小群体定向筛选（丽水仅 4 人被 k=5/8/10/15 抑制） |
| 明细禁令 | `allow_detail=false` 时拒绝非聚合查询 | 外包/分析拉取逐行数据 |
| 关联白名单 | 只允许 schema 声明且策略开放的外键路径 | 借多表 JOIN 绕过列限制 |

> **关于"匿名"的明确声明：遮蔽姓名不等于匿名化。** 准标识符（年龄段+城市+性别等）
> 的组合、外部数据交叉比对、伪标识在同用途内的纵向可链接性，都仍存在重识别风险。
> 本系统通过上述组合控制**降低**风险并满足用途最小化，不声称实现了不可重识别的绝对匿名。

## 3. 版本与原子发布

- 策略文档带 `version`，状态为 `draft / active / archived`，存于 `policies` 表。
- 发布 = 单 SQLite 事务（`BEGIN IMMEDIATE`）：
  建全部新版本视图 → 写策略 → 旧版本归档 → 切 `policy_meta.active_version`
  → 旧导出置 `revoked` → 写审计；失败整体回滚。
- 活动版本是全局单值，**所有用途接口在同一时刻只可能解析到同一个版本**，
  因此规则升级期间不会出现一部分接口按旧范围、一部分按新范围出数。
- 草稿预览走独立连接的 `TEMP VIEW`（固定预览版本号 999999），
  现行版本与草稿各用独立连接对比同一代表场景，预览不触碰正式视图。

### 并发模型

每次数据库操作使用**独立连接**（SQLite WAL：多读者 + 单写者），读不持全局锁；
写事务经写锁串行化并设置 `busy_timeout`，避免共享连接上读写互锁导致的死锁。
测试套件包含 6 线程 × 20 次查询与发布并发执行的回归：期间无错误，
所有响应版本只可能是发布前或发布后的完整版本，不存在读到半成品视图的情况。

## 4. 目录结构

```
app/
  schema.py         原始表/外键路径/运算符与聚合白名单
  policy.py         策略模型、校验、脱敏变换、版本化视图 DDL 生成
  default_policy.py 三用途 v1 规则与收紧演示 v2
  store.py          SQLite、事务化发布、pse() UDF、版本键缓存、审计、预览会话
  executor.py       唯一查询执行边界：编译受限查询 + 列白名单 + k 匿名
  jobs.py           导出任务后台 worker、版本绑定、重启恢复语义
  preview.py        发布前影响评估
  seed.py           虚构数据生成（含 4 人小群体城市）
  init_db.py        建库/灌数/首发 v1
  server.py         标准库 HTTP API + 静态页托管
  main.py           启动入口
  web/              原生 HTML/CSS/JS 页面（无第三方依赖）
tests/test_e2e.py   28 项端到端规则验证（含并发发布回归）
```

## 5. 运行

要求 Python 3.11+（仅标准库，无第三方依赖）。

```bash
# 初始化并启动（--reset 删旧库重建）
python3 app/main.py --reset --port 8000
# 浏览器打开 http://127.0.0.1:8000/

# 端到端规则验证（独立临时库，不影响演示库）
python3 tests/test_e2e.py
```

### 页面操作路径

1. **用途查询工作台**：切换运营/分析/外包，构造过滤、分组聚合或明细查询；
   结果区显示返回行数、被 k 匿名抑制的小组数、缓存命中与实际下发 SQL。
2. **策略规则与发布**：载入版本到 JSON 编辑器 → 改 k/行过滤/列变换 →
   「校验」→「预览影响」（同一场景现行 vs 草稿）→「发布」；
   也可一键生成 v2 收紧草稿（分析 k 5→8，外包 k 10→15、城市 5→3、订单降月度维度）。
3. **导出任务与审计**：提交异步 CSV 导出，观察请求版本/实际执行版本；
   发布后旧任务变 `revoked` 且下载被拒；审计页可追溯每次查询/导出/发布的版本与缓存情况。

### 主要 HTTP API

| 方法/路径 | 作用 |
|---|---|
| `GET /api/purpose/catalog` | 当前活动版本下各用途暴露列、关联、k 值 |
| `POST /api/query` | 结构化用途查询（唯一在线取数入口） |
| `POST /api/query/preview-policy` | 草稿影响预览（不落正式视图） |
| `POST /api/policies/draft` `/publish` | 存草稿（全量校验）/ 原子发布 |
| `POST /api/policies/seed-upgrade` | 生成 v2 收紧草稿 |
| `POST /api/jobs` `GET /api/jobs` `GET /api/jobs/<id>/download` | 异步导出与版本受控下载 |
| `GET /api/audit` | 审计日志 |

## 6. 验证覆盖（`tests/test_e2e.py`，28 项）

原始标识列不存在于任何视图、后端拒绝未暴露列与 SQL 注入标识符、分析/外包明细禁令、
小群体城市被 k 匿名抑制、外包城市白名单、跨用途伪标识不相交、授权/未授权关联、
缓存命中与发布失效、预览隔离、原子发布后全接口统一新版本、旧导出撤回与下载拒绝、
重启恢复任务按新版本重算、非法策略拒绝、**多线程并发查询与发布共存时无死锁且
响应只落在已发布版本上**。
